# Repository Guidelines

## Project Overview

This repository is a workspace for multiple independent Tern plugins. Each plugin is a linkable and publishable Luau package. The repository is not an application and currently has no production plugin instance, build system, test suite, CI workflow, or workspace-level tooling.

The current executable code is only the minimal Window-side template in `templates/basic/window.luau`. Copy it into `plugins/<plugin-id>/` before treating it as a real plugin.

## Architecture & Data Flow

A plugin is declared by `plugin.toml` and may have two independent Luau entry points:

- `host.luau`: session/host side. Use for blocks, command lenses, host hooks, spawn filters, and pane writes.
- `window.luau`: window/UI side. Use for commands, key bindings, overrides, routes, chrome, CSS, and layout.

The two halves run in different Luau VMs. Host-only and Window-only APIs MUST NOT cross the boundary.

Typical flow:

```text
templates/basic/
  -> copy to plugins/<plugin-id>/
  -> edit plugin.toml
  -> tern plugin link
  -> Tern loads host.luau/window.luau
  -> tern plugin list confirms loading
  -> Tern reloads changes, or tern plugin reload is run manually
```

Runtime modules MUST stay inside the plugin directory and use relative `require` paths. Do not create implicit dependencies on the workspace root, a shared root directory, or another plugin.

## Key Directories

| Path | Purpose |
|---|---|
| `plugins/<plugin-id>/` | Independent, installable plugin packages. Current repository has no concrete plugin yet. |
| `templates/basic/` | Minimal Window-side plugin template; copy before development. |
| `docs/` | Workspace design and repository conventions. |
| `references/` | Links to official Tern docs, SDK, examples, and Luau tooling; do not vendor the SDK here. |
| `.agents/skills/` | Project-specific Agent guidance. |
| `.vscode/` | Editor guidance. Per-plugin Tern definitions are expected because API versions may differ. |
| `tooling/` | Reserved for future workspace-level checks; it does not currently exist. |

A plugin normally contains:

```text
plugins/<plugin-id>/
├── plugin.toml
├── host.luau          # optional
├── window.luau        # optional
├── lib/               # optional, plugin-private modules
├── styles/            # optional CSS
├── tests/             # optional checks or fixtures
├── tern.d.luau        # generated by tern plugin types
└── README.md
```

The plugin directory name SHOULD match `plugin.toml.id`. IDs use lowercase letters, digits, and hyphens, start with a letter, and are at most 32 characters.

## Development Commands

Create a plugin from the template:

```sh
cp -R templates/basic plugins/my-plugin
# Edit plugins/my-plugin/plugin.toml: id, name, version
```

Generate Tern type definitions inside the plugin:

```sh
tern plugin types "$PWD/plugins/my-plugin"
```

Run Luau static analysis:

```sh
luau-lsp analyze \
  --platform=standard \
  --definitions=@tern=plugins/my-plugin/tern.d.luau \
  plugins/my-plugin/*.luau
```

Link and inspect one plugin. Do not link the whole `plugins/` directory:

```sh
tern plugin link "$PWD/plugins/my-plugin"
tern plugin list
```

Reload after changes when automatic reload is insufficient:

```sh
tern plugin reload
```

There is currently no documented build command, package-manager command, lint wrapper, formatter, or workspace script. Do not assume Bun, Node, npm, pnpm, yarn, Make, or Cargo is part of this repository.

## Code Conventions & Common Patterns

- Start Luau entry files with `--!strict`.
- Keep `plugin.toml` as the source of plugin identity and entry-point declarations.
- Do not hand-edit generated `tern.d.luau`; regenerate it with `tern plugin types` after Tern upgrades.
- Keep each plugin self-contained. Put reusable code for one plugin in that plugin's `lib/`.
- Keep Host and Window responsibilities explicit. Do not force both halves into one entry merely to share code.
- Follow the official Tern API reference for handler signatures and context capabilities. The local project skill is a navigation aid, not an API substitute.
- Prefer small handlers that update plugin state and return/render through the documented Tern API. Do not introduce a cross-plugin framework before multiple real plugins require one.
- Plugin manifests use `schema = 1`, a unique `id`, `name`, `version`, and optional `description`, `host`, and `window` fields. See `templates/basic/plugin.toml`.
- The template command pattern is `tern.command({ id = ..., title = ..., icon = ..., run = function(cx) ... end })`; UI feedback uses `cx:toast(...)`.
- Plugins can access files and processes. Treat every installed or linked plugin as trusted code and document external commands and permissions in its README.

## Runtime/Tooling Preferences

- Runtime: Tern plus Luau.
- Static tooling: `luau-lsp` with `--platform=standard` and a generated `tern.d.luau` definition file.
- Package manager: none configured in this repository.
- Build system: none configured; Tern loads plugins directly from linked directories.
- SDK policy: keep the official `stencil-hq/tern-sdk` external and use `references/README.md` for navigation. Do not copy the full SDK into this workspace.
- Generated definitions are per-plugin. Point `luau-lsp.types.definitionFiles` at the current plugin's `tern.d.luau`; do not assume one workspace-global definition is valid for every plugin.

## Testing & QA

There is no workspace-wide test runner. The Pane Title native runner requires Tern, Bash, jq, Python 3, and `vi`; its README documents the isolated native-runtime checks.

For a new or changed plugin, use the documented risk-based checks:

1. Confirm `plugin.toml` parses by running `tern plugin types`.
2. Run `luau-lsp analyze` with the plugin's generated `tern.d.luau`.
3. Link only the target plugin and confirm it appears ready in `tern plugin list`.
4. Trigger the changed behavior in a real Tern window or pane.
5. Confirm reload works after editing.
6. Check toast/log output for handler failures.
7. Update the plugin README with purpose, Host/Window choice, link/install command, external commands, and permissions.

A plugin-local `tests/` directory may contain fixtures or executable checks. Document each plugin's runner and command in its README; do not introduce an implicit workspace-level runner.
